Worked interview exercise

Speed up 80 independent lookups

A page must fetch 80 product records from a remote service. Each request takes about 200 ms. The calls are independent, and the caller needs results in the same order as the product IDs. In an interview, explain each decision before writing the next version.

Target: reduce end-to-end time without losing ordering, flooding the service, hiding failures, or leaking worker threads.
Stage 1 · Clarify the problem before optimizing
  • Are the calls independent, or does one result depend on another?
  • Is the time spent waiting on network I/O or doing CPU work?
  • Must result order match input order? Is partial output acceptable?
  • What are the downstream service’s concurrency and rate limits? What is the latency deadline?

Reasoning: concurrency helps independent I/O waits. If the work is CPU-bound, size workers around available processors and measure first.

Stage 2 · Start with a correct, measurable baseline

Establish behavior and timing before changing execution. With 80 calls taking roughly 200 ms each, sequential waiting can approach 16 seconds, excluding overhead.

Sequential baseline · one request completes before the next starts
List<ProductResult> results = new ArrayList<>();
for (String id : productIds) {
    results.add(fetchProduct(id));
}
return results;

Confirm whether this is the actual bottleneck with a representative measurement, not just a guess from the code.

Stage 3 · Parallelize with a bounded worker count

Use a fixed pool of 8 workers as a starting point, submit independent tasks, then read futures in submission order. The result list is written by one thread, so it needs no shared mutable collection.

First parallel version · preserves input order
ExecutorService pool = Executors.newFixedThreadPool(8);
try {
    List<Future<ProductResult>> futures = new ArrayList<>();
    for (String id : productIds) {
        futures.add(pool.submit(() -> fetchProduct(id)));
    }

    List<ProductResult> results = new ArrayList<>();
    for (Future<ProductResult> future : futures) {
        results.add(future.get()); // futures remain in input order
    }
    return results;
} finally {
    pool.shutdown();
}

Do not append to one ordinary ArrayList from worker threads. Also explain that a fixed pool limits active workers, while the standard fixed-pool queue itself is unbounded.

Stage 4 · Add deadline, failures, cancellation, and cleanup

For this finite batch, invokeAll can apply one overall timeout and returns futures in task order. Production code also defines failure policy and shuts down the executor. Assume the enclosing method declares IOException, InterruptedException, and TimeoutException.

Hardened batch shape · Java
ExecutorService pool = Executors.newFixedThreadPool(8);
try {
    List<Callable<ProductResult>> tasks = new ArrayList<>();
    for (String id : productIds) {
        tasks.add(() -> fetchProduct(id));
    }

    List<Future<ProductResult>> futures =
        pool.invokeAll(tasks, 3, TimeUnit.SECONDS);
    List<ProductResult> results = new ArrayList<>();
    for (Future<ProductResult> future : futures) {
        if (future.isCancelled()) {
            throw new TimeoutException("Lookup batch exceeded deadline");
        }
        results.add(future.get());
    }
    return results;
} catch (ExecutionException e) {
    throw new IOException("Product lookup failed", e.getCause());
} finally {
    pool.shutdown();
    try {
        if (!pool.awaitTermination(1, TimeUnit.SECONDS)) pool.shutdownNow();
    } catch (InterruptedException e) {
        pool.shutdownNow();
        Thread.currentThread().interrupt();
    }
}

In a real HTTP client, also set connect/read/request timeouts. Cancellation is cooperative; the fetch operation must respond to interruption or its own timeout. For unbounded input, use backpressure or a bounded ThreadPoolExecutor queue instead of enqueueing every task.

Stage 5 · Measure again and discuss the tradeoffs
  • Compare the same workload before and after. Track throughput and p50/p95 latency, not only one total runtime.
  • Watch pool saturation, queue depth, remote-service throttling, failures, and memory.
  • Try a few pool sizes; eight is a starting hypothesis, not a universal optimum.
  • State the tradeoff: more parallel calls may reduce this caller’s wait while increasing load on the dependency.

Interview close: summarize the bottleneck, correctness guarantees, failure behavior, and what you would measure in production.

See it simply

Tasks go in. Workers do the work.

A task is the work to do. A thread is a worker that runs it. Compare six tasks started as six separate threads with the same tasks handled by an executor that reuses three worker threads.

Starting one thread for each task

Six tasks create six threads. Each thread does one task, then ends.

Simple to picture, but creating many threads adds overhead. Too many can exhaust system resources.
